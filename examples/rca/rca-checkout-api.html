RCA: checkout-api — 502s and DB connection pool exhaustion

System
checkout-api (prod, us-east-1)
Key Identifiers
checkout-api-7d9f pods · orders-db primary · ALB chk-prod
First seen
2026-10-14 18:02 UTC

Issue 1: 502s during peak, suspected ALB idle timeout False positive

502 Bad Gateway on POST /v1/checkout, ~4% of requests between 18:00–18:40 UTC.

Investigation

ALB access logs showed elb_status_code=502 with target_processing_time=-1, which usually means the target closed the connection. The ALB idle timeout (60s) was lower than the app's keep-alive (75s), which looked like a classic mismatch.

Root Cause

ALB idle timeout shorter than the upstream keep-alive, so the ALB reused sockets the app had already closed.

Fix

aws elbv2 modify-load-balancer-attributes \
  --load-balancer-arn "$CHK_ALB_ARN" \
  --attributes Key=idle_timeout.timeout_seconds,Value=90

Result: 502 rate unchanged the next evening.

Update (2026-10-16): This was a false positive.

Why it appeared to be the cause: The timeout mismatch was real but harmless. The 502s lined up with pods failing readiness, not with idle sockets.

Actual cause: See Issue 2.

False positive

Issue 2: Connection pool exhausted by un-released transactions Resolved

HikariPool-1 - Connection is not available, request timed out after 30000ms, then readiness probe failures and pods dropping out of the target group.

Investigation
  • pg_stat_activity showed 40/40 connections idle in transaction during the spike.
  • Dead end: raising maximumPoolSize to 80 only delayed exhaustion by ~6 minutes.
  • Every stuck session's last query was SELECT … FROM coupons FOR UPDATE, added in the 2026-10-13 coupon-stacking release.

Root Cause

The coupon validator opened a transaction, then made an HTTP call to the pricing service inside it. When pricing slowed at peak, each request held a row lock and a pool connection for up to 30s.

Fix

git revert 3f1c9a2   # move pricing call outside the transaction
kubectl -n checkout rollout restart deploy/checkout-api
kubectl -n checkout rollout status deploy/checkout-api

Result: Zero idle in transaction sessions over 1s; 502 rate 0.00% through the 2026-10-17 peak.

Runbook

  1. Check for sessions holding transactions open: 
    psql "$ORDERS_DB_URL" -c "select pid, now()-xact_start as age, left(query,80)
  from pg_stat_activity where state='idle in transaction' order by age desc limit 20;"
    Verify: any age over a few seconds is the smoking gun.
  2. Confirm pods are leaving the target group, not just erroring: 
    kubectl -n checkout get events --field-selector reason=Unhealthy --sort-by=.lastTimestamp | tail
  3. Before changing load-balancer settings, correlate 502 timestamps with readiness failures.

Learnings

  • Never make network calls inside a DB transaction. Latency elsewhere turns into lock and pool exhaustion here.
  • A real misconfiguration isn't automatically the cause. Check that it lines up with the symptom's timing before you call it the fix.
  • A bigger pool is a timer, not a fix. If raising the limit only delays failure, something is leaking.
